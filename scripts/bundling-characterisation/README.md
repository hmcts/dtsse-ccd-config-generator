# Bundling characterisation harness

Generates the rendering-parity **golden outputs** for `sdk/document-bundling` by running
[em-stitching-api](https://github.com/hmcts/em-stitching-api)'s **real rendering classes** —
`PDFMerger`, `TableOfContents`, `PDFOutline`, `PDFWatermark`, `PDFUtility` from
`uk.gov.hmcts.reform.em.stitching.pdf` — against the service's **own test fixtures**, exactly as
its unit tests do, and recording per scenario the output PDF plus its extracted semantic facts.

See the design doc section *"Regression baseline: characterisation against the local
em-stitching-api"* in `docs/bundling-stitching/document-bundling-module-design.md`.

| PDFBox | 3.0.8 (same as the service) |
| JDK | 21 |

The checkout is expected at `../../../em-stitching-api` (a sibling of this repository); override
with `-PemStitchingDir=/path/to/em-stitching-api`. The checkout is **read-only input**: sources
are compiled straight out of it and fixtures are read from
`src/test/resources/test-files`; nothing in it is ever modified (fixtures are copied to a temp
directory before any mutating operation — `PDFWatermark` saves over its input file in place).

## How it works

This is a standalone Gradle build — it is intentionally **not** registered in any
`settings.gradle` of this repository.

* `build.gradle` adds the em-stitching checkout's `src/main/java` as a source directory and
  compiles only the rendering package (`pdf/**`) plus the minimal domain closure it needs
  (`Bundle`, `BundleDocument`, `BundleFolder`, `BundleContainer`, `SortableBundleItem`,
  `DocumentImage`, `AbstractAuditingEntity`, and the `PaginationStyle`/`PageNumberFormat`/
  `ImageRendering*` enums). The JPA/Hibernate/Spring annotations those sources carry are
  satisfied with compile-time dependencies; a tiny stub of
  `config.audit.EntityAuditEventListener` (in `src/stub/java`) replaces the one class that would
  otherwise drag in the service's repositories. No em-stitching jar needs to be built.
* The SDK module's semantic extractor
  (`sdk/document-bundling/src/test/java/.../testsupport/PdfSemantics.java`) is compiled into the
  harness from its real location, so goldens are generated by the **same code** future SDK
  regression tests use for comparison.
* `CharacterisationHarness` ports the bundle constructions from em-stitching's own
  `PDFMergerTestUtil`/`PDFMergerTest`/`PDFMergerCoversheetsTest`, runs the real merger/watermark,
  and writes per scenario:
  * `facts.json` — the authoritative comparison artifact (schema below);
  * `golden.pdf` — the raw em-stitching output (informational; regenerating produces different
    bytes but byte-identical facts — verified by running the harness twice and diffing).

## facts.json schema

Produced by `PdfSemantics.extract` (see its javadoc for the authoritative description):

| field | content |
|---|---|
| `pageCount` | total pages |
| `pageLabels` | catalog page-label dictionary per page, or `null` when absent (em-stitching never sets labels) |
| `pages[].text` | per-page text, **position-sorted** (`PDFTextStripper.setSortByPosition(true)`) and **whitespace-normalised** (lines trimmed, internal whitespace collapsed to one space, empty lines dropped, joined with `\n`) — draw order and glyph spacing are tolerated by construction |
| `pages[].pageNumberStamps` | visible page-number stamps: `{value, x, y}` (rounded PDF-space line origin). Bounded heuristic: a line of **1–4 digits** whose baseline is **within 60pt of the top or bottom page edge** (all six em-stitching `PaginationStyle` positions print ~20pt from those edges). Long digit runs (CCD case references) and mid-page digits (chart axis labels) are never stamps |
| `pages[].images` | every image XObject reachable from the page (recursing into form XObjects, as PDFBox `Overlay` nests watermarks): `{width, height, pixelSha256}` where the hash is `px:`+SHA-256 of the **decoded ARGB raster** (survives recompression between producers; `raw:`+stream-bytes hash as fallback), sorted by (hash, width, height) |
| `outline` | full outline tree: `{title, bold, targetPage (1-based or null), children}` |
| `links` | link annotations: `{sourcePage, rect [llx,lly,urx,ury rounded], targetPage (1-based or null)}` |

Outputs land in `sdk/document-bundling/src/test/resources/characterisation/<scenario>/`.

## Regenerating

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)
cd <repo root>
./gradlew -p scripts/bundling-characterisation run
```

Optional properties: `-PemStitchingDir=...` (checkout location), `-PoutputDir=...`
(defaults to the module's `src/test/resources/characterisation`),
`-PwriteGoldenPdfs=false` (facts only).

Regeneration is a **manual, documented step**: when regenerating against a newer em-stitching
SHA, update the commit in the table above and review the facts diff — every change is either an
upstream behaviour change to characterise or a harness bug.
`PdfSemanticsTest.extractionRoundTripsAgainstCommittedCharacterisationGoldens` in the module then
verifies each committed `golden.pdf` still extracts to exactly its committed `facts.json`.

## em-stitching behaviours captured by the goldens (watch-outs)

Characterising surfaced behaviour that looks defective or surprising; the goldens pin it as-is:

* **Source outlines are dropped unless document subtitles are enabled** —
  `PDFOutline.copyOutline` returns before copying any children when
  `hasDocumentSubtitles=false` (`preserved-outlines` has no source outline entries;
  `document-subtitles-outlines` does).
* **Named destinations break after merge** — the merged document gets no names dictionary, so
  copied outline entries and link annotations that used named destinations resolve to nothing
  (`targetPage: null` in `document-subtitles-outlines` and `preserved-outlines`).
* **TOC subtitle entries can link to a detached page** — `TableOfContents.getDestinationPage`
  returns `new PDPage()` (not in the page tree) for unresolvable or out-of-bounds destinations,
  producing links that navigate nowhere.
* **`PDFWatermark` overwrites its input file in place** (`document.save(documentFile)`), and
  swallows all errors — on failure it returns the original document silently. Worse, saving
  over the file it is still lazily reading **corrupts the output's text layer**: the
  `image-watermark` golden's `pages[].text` is stream garbage. The SDK will produce readable
  text there, a deliberate divergence — on watermarked pages the image facts must match the
  golden and text readability is expected to *exceed* it (see the policy in
  `CharacterisationRegressionTest`).
* **Title sanitisation is lossy and asymmetric** — `PDFUtility.sanitizeText` silently drops
  every non-WinAnsi character from drawn text (the `special-character-titles` TOC renders
  "ąćęłńóśźż" as just "ó") while the same title is stored intact in the outline.
* **The cover-sheet "Back to index" link is drawn off-page** (swapped-argument position), so
  its golden link rectangle is outside the media box; the SDK replaces it with an on-page
  clickable link (policy divergence 10).
* **Page-number stamps are page-relative, label-free** — printed as plain integers from the
  overall page index; no PDF page labels are ever set (`pageLabels: null` everywhere).

The full per-field comparison policy — what is pinned exactly, what is tolerated by
construction, and the enumerated deliberate divergences (source-outline preservation, named
destinations, TOC format, watermark behaviour, link-rect tolerance: target page exact, rect
within page bounds, coordinates otherwise free) — lives in the javadoc of
`uk.gov.hmcts.ccd.sdk.bundling.testsupport.CharacterisationRegressionTest`.
